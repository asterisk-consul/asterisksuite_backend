# Plan: Activar RBAC en Asterisk Suite Backend

## Estado actual

La infraestructura RBAC **ya existe pero está desconectada**:

- **Schema Prisma**: `permissions`, `business_roles`, `business_role_permissions`, `business_user_roles`, `user_permission_overrides` → `prisma/models/roles.prisma`
- **Guard**: `PermissionsGuard` con `@RequirePermissions()` → `src/access-control/guards/permissions.guard.ts`
- **Context Builder**: carga permisos del usuario en memoria por request → `src/access-control/authorization/permission-context.builder.ts`
- **Services**: `RolesService`, `PermissionsService`, `AuthorizationService` → `src/access-control/services/`
- **Controllers CRUD**: roles, permissions, users, rbac-test → `src/access-control/controllers/`

**Problemas:**
1. Ningún controller usa `@RequirePermissions()` → cualquier usuario autenticado accede a todo
2. Los endpoints de access-control **no tienen ni JwtAuthGuard** → completamente abiertos
3. No hay seed de permisos ni roles iniciales
4. No existen modelos de cajas/sucursales

## Fase 1: Conectar el RBAC existente

### Paso 1.1 — Proteger endpoints de access-control

**Archivos a modificar:**
- `src/access-control/controllers/roles.controller.ts`
- `src/access-control/controllers/permissions.controller.ts`
- `src/access-control/controllers/users.controller.ts`
- `src/access-control/controllers/rbac-test.controller.ts`

**Acción:** Agregar `@UseGuards(JwtAuthGuard, PermissionsGuard)` a nivel clase y `@RequirePermissions(...)` por método.

**Ejemplo para `RolesController`:**
```ts
import { UseGuards } from '@nestjs/common';
import { JwtAuthGuard } from 'src/auth/jwt/jwt-auth.guard';
import { PermissionsGuard } from 'src/access-control/guards/permissions.guard';
import { RequirePermissions } from 'src/access-control/decorators/require-permissions.decorator';

@UseGuards(JwtAuthGuard, PermissionsGuard)
@Controller('access-control/roles')
export class RolesController {
  // ...
  @Get()
  @RequirePermissions('roles.read')
  findAll() { ... }

  @Post()
  @RequirePermissions('roles.create')
  create(@Body() dto: CreateRoleDto) { ... }

  @Patch(':id')
  @RequirePermissions('roles.update')
  update(...) { ... }

  @Delete(':id')
  @RequirePermissions('roles.delete')
  remove(...) { ... }

  @Put(':id/permissions')
  @RequirePermissions('roles.manage_permissions')
  updatePermissions(...) { ... }
}
```

**Permisos por controller:**

| Controller | Endpoint | Permiso |
|---|---|---|
| RolesController | GET / | `roles.read` |
| RolesController | GET /:id | `roles.read` |
| RolesController | POST / | `roles.create` |
| RolesController | PATCH /:id | `roles.update` |
| RolesController | DELETE /:id | `roles.delete` |
| RolesController | PUT /:id/permissions | `roles.manage_permissions` |
| PermissionsController | GET / | `permissions.read` |
| PermissionsController | GET /:code | `permissions.read` |
| UsersController | GET /:userId/roles | `users.read_roles` |
| UsersController | PUT /:userId/roles | `users.assign_roles` |
| UsersController | GET /:userId/permissions | `users.read_permissions` |
| RbacTestController | POST /can | `roles.test` |

### Paso 1.2 — Registrar PermissionsGuard como provider global

**Archivo:** `src/access-control/access-control.module.ts`

El `PermissionsGuard` necesita estar disponible en todos los módulos. Opciones:
- **Opción A (recomendada):** Registrar como provider global en `AppModule` con `@Global()` o `APP_GUARD`
- **Opción B:** Importar `AccessControlModule` en cada módulo que necesite permisos

Se usa **Opción A** con `APP_GUARD` para que esté disponible automáticamente:

```ts
// En AccessControlModule, agregar:
import { APP_GUARD } from '@nestjs/core';

providers: [
  // ... existentes
  { provide: APP_GUARD, useClass: PermissionsGuard },
]
```

Con esto, `PermissionsGuard` se ejecuta globalmente. Si un controller no tiene `@RequirePermissions()`, el guard deja pasar (ya tiene esa lógica: `if (!requiredPermissions) return true`).

## Fase 2 (futura): Cajas y Sucursales

Esto requiere nuevos modelos Prisma. La idea es un sistema de **scope-based permissions** donde un permiso puede estar limitado a una caja o sucursal específica.

### Modelo conceptual (no implementar ahora, solo documentar):

```prisma
model branches {          // Sucursales
  id, company_id, code, name, address, active, ...
}

model cash_registers {    // Cajas
  id, branch_id, code, name, active, ...
}

model user_branch_access {    // Acceso usuario → sucursal
  user_id, branch_id, role_override?
}

model user_cash_register_access {  // Acceso usuario → caja
  user_id, cash_register_id, branch_id
}
```

El `PermissionContextBuilder` se extendería para incluir scoping:
```ts
can(permission, { branchId?, cashRegisterId? }) → boolean
```

## Verificación

1. **Seed:** ejecutar `npx prisma db seed` o `ts-node prisma/seeds/rbac.seed.ts` → verificar que permisos y roles existen en DB
2. **Sin token:** `GET /api/master-data/products` sin Authorization → 401
3. **Sin permiso:** login como usuario con rol `user` (solo lectura) → `POST /api/master-data/products` → 403
4. **Con permiso:** login como usuario con rol `admin` → `POST /api/master-data/products` → 201
5. **Access-control protegido:** `GET /api/access-control/roles` sin permiso `roles.read` → 403
6. **Override DENY:** asignar override DENY a usuario para `products.read` → `GET /api/master-data/products` → 403 aunque tenga rol admin
7. **Test endpoint:** `POST /api/access-control/test/can` con `{ userId, permission: "products.create" }` → devuelve `allowed: true/false`
